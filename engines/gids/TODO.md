# GiDS：Tutti 使用模式覆盖 TODO

状态：方案待实施。下列复选框均为待办，不代表已有参数、功能或验收结果。
现有插件构建入口见 [BUILD.md](BUILD.md)。

## 目标与边界

让 fio 复用 Tutti 的实际 I/O 提交路径，测量多盘融合提交、worker 池、
读写并发以及与 GPU 计算的资源竞争。目标调用关系：

```text
fio -> gids.so -> 现有直接访问后端（PCIe / RDMA）
              -> 可选 Tutti 适配后端 -> StorageRuntime -> DataPath
```

这里的“Tutti Runtime 后端”指调用 Tutti 库的适配层。vLLM 当前通过
`make_local_nvme_runtime()` / `make_striped_nvme_runtime()` preset 构造
`StorageRuntime`；首版优先复用这条路径，不引入 Python connector 或 PyTorch。
它与包含 Resource/lease 管理的最外层 `TuttiRuntime` 装配入口有所区别，
需要在部署说明中明确盘由谁接管、client 如何 attach、资源由谁释放。

- 保留外部 ioengine 形式，首版不修改 fio 核心。
- 尽量使用 Tutti 公开接口，不复制其队列算法或另写一套融合 kernel。
- 如发现接口或构建缺口，只提交必要的小补丁，并保留贡献回 Tutti 的边界。
- 后端选择与 `pcie/rdma` 传输类型分别表达；具体参数名在实现时确定。
- 首版覆盖本地 NVMe；现有直接访问 RDMA 的验证不能替代 Tutti 后端验收。
- KV 命中、vLLM block 生命周期、TP 协调和模型输出正确性继续由 E2E 验收。

## 开发和提交规则

- [ ] 将 Runtime 后端作为独立扩展开发，保持各阶段范围清楚。
- [ ] 每个实现提交有一个明确目的，同时带上构建入口、使用说明和验证方法。

以下阶段是提交拆分的建议边界；若一个阶段需要拆分，拆出的提交也必须可独立验证。

## 1. 单卡单盘：接通公开 Runtime 接口

目的：证明适配层能够在 fio 内安全运行真实 Tutti 数据通路。

- [ ] 增加可选构建依赖和后端入口；未启用时仍可构建现有 GiDS 插件。
      检查 MACA SDK、PIC/device linking、依赖符号及动态加载。
- [ ] 实现目标打开、GPU buffer 分配与注册、请求转换、批量提交和资源释放。
      首版只允许一个在途批次，保持调度模型可验证。
- [ ] 用 `query()` 驱动有界进度查询，再读取最终结果；不能把
      `wait(handle, 0)` 当成能够推进 I/O 的轮询接口。
- [ ] 处理部分接受、容量不足和不可重试错误：逐项读取 `initial_states`，
      保留已接受请求的归属；拒绝项明确重试或报错，不能丢失或重复完成 fio 请求。
- [ ] 对齐 fio 超时与 Tutti 生命周期：观察超时不等于设备 I/O 已取消；
      确认在途 I/O 排空后再释放 GPU buffer、DMA 注册、目标及 runtime。
- [ ] 提供专用测试文件准备流程。文件预分配、落盘和 extent 校验在计时前完成；
      不将现有裸盘接管流程直接用于 daemon 已接管并挂载的盘。

独立验收：

- [ ] 在 Linux/MACA 上完成后端开/关两种构建、插件路径加载及参数帮助检查。
- [ ] 单盘 4 KiB / 128 KiB 读取与参考数据逐字节一致；写后读回仅使用专用测试文件。
- [ ] 验证部分拒绝、容量背压、超时、初始化失败和退出清理；
      每个 fio 请求恰好返回一次结果，失败项不得计作成功。
- [ ] 保存实际源码版本、SDK/驱动、设备身份、命令和原始日志；
      基础接入先在 N300 验证，C500 单独记录兼容性结果。

## 2. 单卡多盘：一个 job 融合提交

依赖：阶段 1。目的：一个 fio job 对应一个 rank 的多盘 I/O 上下文。

- [ ] 扩展“每 job 一个 namespace”的限制，将每个 fio 文件映射到独立 target。
      分别处理文件大小、偏移边界、设备身份和错误，不能共用一份单盘 geometry。
- [ ] 使用多盘 preset，让一次批量提交包含不同 SSD 的目标，复用融合 kernel。
      保留每条请求的文件身份和完成映射。
- [ ] 明确 fio 如何形成跨盘批次；记录提交次数、kernel 次数和每盘请求分布，
      避免把多个独立 job 的并发误当成一次融合提交。

独立验收：

- [ ] 单 GPU + 2 SSD，逐盘核对数据、请求数、字节数和错误；具备设备后扩展到 4 SSD。
- [ ] 用正常、不触发额外拆分的批次核对“一次 submit 对应一次融合 launch”。
- [ ] 覆盖不均匀盘负载、单目标请求被拒绝及部分初始化失败后的清理。
- [ ] 同时保留各盘统计与总量，性能结果注明批次大小和实际执行重叠。

## 3. 将队列、worker 和批次容量分别配置

依赖：阶段 2。目的：测量真实 Tutti 并发模型的资源开销。

- [ ] 分别暴露并说明每盘队列数、worker 数、批次容量和在途批次配额。
      fio `iodepth` 仍表示 fio 请求在途数量，不能与上述参数互相替代。
- [ ] 复用 Runtime 的 worker-pool 路径和容量约束；支持查询、记录实际生效值。
      直接 PCIe 后端的单 QP 批次并不包含 Runtime worker 池，不能替代此模式。
- [ ] 按准入容量执行背压，记录显存和队列使用；明确 Runtime 一个批次的完成
      粒度与 fio 单请求统计之间的对应关系。

独立验收：

- [ ] 对照少量/较多 worker、少量/较多队列及不同批次大小；验证资源不足时行为。
- [ ] 优先验证多个 worker 共享少量队列、队列回绕、重复批次和超时恢复。
      现有 GiDS 曾通过拆分批次规避共享队列争用，不能把它的通过结果外推到新模式。
- [ ] 先通过数据与计数校验，再报告吞吐、尾延迟、显存和 GPU 资源占用。

## 4. 读写 stream、多个在途批次与层计划重放

依赖：阶段 3。目的：覆盖 connector 的 I/O 流水线和依赖顺序。

- [ ] 扩展当前“整个批次回收完再提交下一批”的状态机，允许多个批次在途。
      buffer slot 只能在对应 I/O 完成后复用。
- [ ] 支持独立读写 stream，明确是否允许读写重叠以及写等待读的事件策略。
- [ ] 定义带文件/设备、chunk、layer、方向和批次边界的回放格式。
      普通 fio `read_iolog` 不表达 GPU 层依赖，需要配套计划或协调机制。
- [ ] 加入逐层完成事件，保证消费者只在本层数据可用后继续。
      固定计划重放与可持续执行的随机负载分别定义结束条件。
- [ ] 决定批量计时接口：当前 `gids_ap_latency` 只支持 QD1，不能直接用于
      新的多 worker/多批次模式；fio 延迟、批次延迟和 GPU 内部时间分别报告。

独立验收：

- [ ] 使用已知内容和依赖序列验证层顺序、读写顺序及 buffer 复用，无遗漏、重复或提前完成。
- [ ] 在延迟完成和部分失败情况下验证背压、批次回收和退出排空。
- [ ] 对比逐项回放结果与参考计划，并用事件/设备时间线确认依赖和重叠。

## 5. 同进程 GPU 计算与 I/O 干扰

依赖：阶段 4。目的：量化 I/O 对计算及计算对 I/O 的影响。

- [ ] 在同进程、同 GPU 的计算 stream 上加入可重复的计算负载。
      复核 Tutti 已有 `launch_sgemm` 是否满足测试需求；简单模拟不能视为完整模型。
- [ ] 分别运行纯计算、纯 I/O、并发三组；固定计算规模、数据量、盘拓扑和 I/O 配置。
- [ ] 同时记录计算耗时、I/O 带宽/延迟、GPU 执行重叠及测试环境状态。
      CPU `thinktime` 不能替代 GPU 计算负载。
- [ ] 默认使用普通 stream；CUDA green context 等资源隔离能力另行检测和验收，
      不假设 N300/C500 支持，也不把 worker 数换算为固定计算单元占比。

独立验收：

- [ ] 计算结果和 I/O 数据都正确，时间线显示真实执行关系，资源清理完整。
- [ ] 报告计算变慢比例、I/O 变慢比例和重复运行波动；不直接推断 TTFT/ITL 收益。
